# Sync protocol

How the facilitator's browser (the host) and participants' browsers stay in step. This is protocol version **4**. Protocols 3 and 4 use protocol 2's wire layout (the plaintext bytes below). Protocol 3 differs from 2 in the names of the board's and the messages' fields; protocol 4 adds one facilitator command, `undoMoveOn` (lean-coffee-rules.md), which changes no field or layout. The code is in `src/protocol/`, `src/session/` and `src/transport/`.

The board rules, and what each person may see, are in [lean-coffee-rules.md](lean-coffee-rules.md). This document covers how those views and the commands travel.

## Paths

Every participant reaches the host in one of two ways, and may switch between them during a meeting.
- **The relay path** is ephemeral Nostr events (kind 20333) published to every relay in `src/config.ts`. Every subscriber in the room receives every event. The host publishes every change to the relays, whoever is connected directly.
- **The direct path** is a WebRTC data channel (Trystero, with Nostr signalling), used as well where it connects. Messages on it go to one peer.

Relay events carry a frame, `{from, to?, d, e?}`: `from` is the sender's transport ID, `to` the intended transport peer (left out for broadcasts), `d` the sealed message in base64url, and `e: 1` marks a ping that the sender wants echoed back to itself (see Pings). The transport ID (`peer`) is random per page load. The room's relay topic and WebRTC room ID are hashes of the room key, so relays never see the key.

## Layers

1. **Envelope:** `{v: 1, pub, body, sig}`. `body` is the JSON message as a string, and `sig` is an ECDSA P-256 signature over exactly that string. The sender's person ID is the fingerprint of `pub`.
2. **Plaintext:** in protocol 2, the byte `0x02` followed by the envelope's JSON, compressed with `CompressionStream('deflate')`. In protocol 1 it was the envelope's JSON as UTF-8, with no prefix, so its first byte is `{`. The relay bundle has its own binary layout, marked `0x03` (see [The relay bundle](#the-relay-bundle)).
3. **Wire:** the plaintext sealed with AES-GCM under the room key from the share link, with a fresh 12-byte IV.

A receiver reads the first byte of the plaintext: `0x02` and `0x03` are protocol 2, `{` is protocol 1, and anything else is dropped. Only two messages ever use protocol 1: every `hello`, so that a host of any version can read it, and the version reply (see Protocol version).

## Messages

### Participant to host

| Message | Path | Meaning |
| --- | --- | --- |
| `hello {pv, boardId, name, peer, sid, n, at}` | Relay broadcast, and direct when a host peer is known; while the host is unknown, to every direct connection as well | "I'm here." `pv` is the sender's protocol version (4); a hello without `pv` is protocol 1. `boardId` is the meeting from the share link. `peer` is the sender's transport ID. A protocol 2 hello also names its tab (`sid`), counts the tab's hellos from 1 (`n`, one per hello sealed) and carries the sender's estimate of the host's clock (`at`; before the page has a clock reading it uses the host time shown by the newest verified bundle header or by a newer snapshot from the host peer over the direct path, else its own time); the host accepts a hello only if it is fresh (see Pings) |
| `cmd {boardId, peer, clientSeq, sid, epoch, cmd}` | Direct if proven, otherwise relay to the host's peer | A board command. `peer` is the sender's transport ID, which the host checks against the peer it arrived from, like a ping's. `sid` is the tab; `clientSeq` counts that tab's commands from 1; `epoch` is the host session the sender last heard from |
| `ping {boardId, sid, n, at, t0, peer}` | Direct if proven, otherwise relay with `e: 1` | Liveness and clock. `boardId` is the meeting; `sid` the tab and `n` its pings counted from 1; `at` the sender's estimate of the host's clock; `t0` the sender's own clock, never repeated; `peer` its transport ID |

**Tab IDs.** A `sid` is made on every page load as `{creation time in ms, base 36}.{9 random bytes, base64url}`, for example `mg3k1x2a.Q2x1Y2tlZEJy`. Its creation time is what the host's pruning watermark compares (see Pruning).

### Host to participant

| Message | Path | Meaning |
| --- | --- | --- |
| `snapshot {epoch, seq, hostNow, you, host, state}` | Direct, one per peer | The full view for one person. `state` is a `ViewState` (below). `you` is the recipient's person ID; `host` is the host's transport ID |
| `pong {t0, t1}` | Direct only | Answer to a direct ping. `t1` is the host's clock |
| `bundle {epoch, seq, refreshSeq, hostNow, host, boardId, shared, items, itemsHash}` | Relay, for everyone | The board for every relay reader at once (below) |

`hostNow` is monotonic within a host session: each message takes `max(Date.now(), previous hostNow + 1)`.

## The views

### `ViewState`

What `redactFor(state, viewerId)` returns, and what a direct snapshot carries. It is built from the **last saved** state, never from a change that hasn't been saved yet.

| Field | Meaning |
| --- | --- |
| `boardId`, `boardName`, `phase`, `voteAllowance`, `showVotes`, `rehearsal`, `timerSound`, `endedAt`, `discussedOrder` | As in the host's state |
| `topics[]` | `{topicId, text, column, position, authorId, votes?, mine}`. `votes` is the count, left out where the rules hide it; `mine` is the viewer's own dots on that topic |
| `attendees` | `{id: {id, name, role}}` |
| `online` | Person IDs heard from in the last 15 s, the host included |
| `timer` | `{topicId, startedAt, endsAt, round, minuteMs}` or `null`, on the host's clock |
| `vote` | `{topicId, round, voted, turnout: {voted, here}, totals?}` or `null`. `voted` is whether this viewer has voted. `totals` is `{extend, none, end}`, present for facilitators and for viewers who have voted |
| `role` | The viewer's own role |
| `acks` | `{sid: clientSeq}` for the viewer's tabs (see Acks and rejects) |
| `rejects` | `{sid: {clientSeq, key}}`, the last refused command per tab, where `key` is a key of `src/engine/messages.ts`. The participant shows that message; an unknown key shows `badCommand` |
| `joinRefused` | A message key, present only in a view for someone whose join was refused (see Joining) |

`voteRound`, `topicIdSeed`, the vote's `voters` list and every voter ID are never in a view.

### The relay bundle

The bundle is the same view, split so the host can send one event to everyone.

- **`shared`** is the viewer-neutral part, identical for everyone: every `ViewState` field except `role`, `acks`, `rejects` and `joinRefused`, with topics carrying `votes` but not `mine`, and `vote` carrying `topicId`, `round` and `turnout` but not `voted` or `totals`. While Show votes is off in the topics phase, `votes` is left out of Ideas topics for everyone.
- **Personal entries** carry only what differs per person: `personal {epoch, seq, you, host, role, mine, voted, totals?, acks, rejects, joinRefused?}`, where `mine` is `{topicId: dots}` for topics this person has dots on, `voted` is whether they have voted in the open time-up vote, and `totals` is present for facilitators and for people who have voted.
- **Binary layout.** The bundle's plaintext, before the outer seal, is:
  1. the byte `0x03`;
  2. a 4-byte big-endian length, then the deflated JSON envelope of the `bundle` message, signed by the host's key;
  3. the items, back to back, each a 2-byte big-endian length then the item's bytes.

  Each item is `seal(roomKey, 0x04 + sig + deflate(body))`, where `body` is the `personal` message's JSON and `sig` is the host's raw 64-byte ECDSA signature over that JSON's exact UTF-8 bytes. Items carry no public key: only the host's key `h` can have signed them. The `bundle` message's `items` is the number of items and `itemsHash` is the base64url SHA-256 of the whole item section, so the outer signature covers every item. Nothing is base64-encoded twice: the only base64 is the frame's `d`.
- **Combining.** A participant opens the items one by one and keeps the one whose `you` is their own ID; that costs a handful of AES operations. `shared` plus that entry gives exactly the `ViewState` that `redactFor` builds. A unit test checks this for every viewer in a fixture.
- **Recipient names stay inside the seals.** Neither the frame nor anything outside an item's seal names a person, so relays can't link a device across meetings.
- **Full refreshes and `refreshSeq`.** A *full refresh* carries an entry for every attendee other than the host who is bound to a peer record (a neutral entry, with no dots, ballot, totals, acks or rejects, while all of that person's records are probationary), plus refused joiners, up to `REFUSED_ENTRIES_MAX`. An attendee with no record gets no entry until their next hello binds one. Any other bundle may leave out the entries of people whose personal part hasn't changed since the last full refresh. Every bundle names the `seq` of the last full refresh as `refreshSeq` (a full refresh names its own `seq`). So a participant who misses a bundle that changed their entry gets it again in the next bundle, and at the latest in the next refresh.
- **No half-delivered changes.** A change travels as one event, so a participant sees all of it or none of it.

### Size

A relay event must stay under **48 KB**, measured as the length in bytes of the final Nostr event JSON (`id`, `pubkey`, `created_at`, `kind`, `tags`, `content` holding the frame, and `sig`). The host keeps a full refresh, with every personal entry, at or under **44 KB**, leaving 4 KB of headroom.

**The size cap is measured with an upper bound.** Before the host commits `addTopic`, an `editTopic` that makes a topic longer, or a `join` that adds an attendee or lengthens a name, it measures the largest full refresh the new state can lead to without another growing command: an upper bound on the length of the Nostr event that refresh would make, worked out from two real deflates and fixed overheads (below). Over 44 KB, the command is refused (`boardFull` for topics, `meetingFullSize` for joins) and the board is unchanged.

The bound covers everything that can change without being measured again:
- **The shared part:** everyone online, every count shown at the most the largest vote allowance allows, every topic in the longest column and discussed, the longest phase and sound, a timer and a vote with the longest numbers, and an end time.
- **The entries:** every attendee but the host gets an entry with every field at its largest: the largest allowance of dots on different topics, the longest role, totals, three acks and three rejects with the longest sids, numbers and message key, and a refused join.
- **Refused joiners:** three more entries, the most a bundle ever carries.

IDs, sids and numbers are random stand-ins at their longest length, because deflate shrinks repeated text and real IDs are random. A margin of 2 % plus 256 bytes covers what compression can still vary.

**How the bound is computed.** The meter builds the stand-in bundle's messages but seals, signs and hashes none of them. It deflates, for real, the bundle's outer message (the shared part, with a placeholder key, signature and hash of their fixed lengths) and one entry, which names a random 22-character person (a live joiner's ID is a 22-character fingerprint). An entry whose person's ID is any other (an imported board can hold IDs of any content, up to 1,280 characters) is deflated for real on its own, so a board with unusual IDs costs one more deflate for each and is never under-measured; on a live board that costs nothing. Every other length is a fixed overhead that cannot vary: per entry 12 (IV) + 16 (GCM tag) + 1 (marker) + 64 (signature) + 2 (length) bytes, for the bundle 12 + 16 + 1 + 4 bytes, base64url at 4 characters per 3 bytes, and the event's fixed-length id, key and signature, frame and tags. Entries with a fingerprint for an ID differ only in the random sids and numbers of their acks and rejects, which move a deflated entry by a few bytes (about 390 bytes, a standard deviation of 2.4 and a spread of 15 over 300 samples in a one-off measurement; the test checks at most 24 over 150), so each such entry is taken to be the measured one plus 24 bytes (and each odd-ID entry its own deflate plus 24), and never more than a stored (uncompressed) deflate block would take. The slack adds up to 24 bytes (32 in base64url) for each entry, so up to 2 KB for 60 people and about 0.9 KB for the 15-person realistic board, on top of what the earlier meter, which sealed every entry, measured. Tests prove it: the layout and overheads equal a real bundle's byte for byte; the meter is never below the real, sealed stand-in refresh for boards of every shape (incompressible, repetitive and random text, one to 60 people, up to 60 topics); and the property test in `src/session/refresh-size.test.ts` still holds the figure against the host's real sender. So votes, acks, rejects, presence, phases and timers can never push a board over after the check.

**The ceiling.** The sender also checks every bundle it builds. If one would still pass 48 KB, it leaves out, in this order, until it fits:
1. every ack and reject but each person's newest tab's (older tabs' commands are resent and acknowledged later);
2. the entries of people whose every tab is on a healthy direct path, who get a direct snapshot anyway (a person with a relay-only tab keeps their entry), keeping refused joiners' entries;
3. refused joiners' entries (they say hello again).

An attendee's entry is never left out to make room for a refused joiner's. So a refused joiner is told why, even when the ceiling is hit, as long as a bundle with every relay-only attendee's entry and the refusal fits. **Known limit:** when the bundle with every relay-only attendee's entry plus the refusal does not fit, but fits without the refusal, the refused joiner's entry is left out and that joiner is left on "Still trying to reach the facilitator" (a direct snapshot still reaches a joiner with a direct path; a joiner who says hello again may be refused again). This can happen in a mixed room as well, if the direct-path people's entries were not enough to make room. Reaching it takes a board the size meter would not have let grow, so it should never happen.

If it still doesn't fit (the bundle with every attendee's entry but the direct-path people's), that bundle goes out regardless, refused joiners' entries included, so a relay that accepts it still carries the reason; being over is what sets the signal below. The host warns, shows the facilitator a banner, counts each such bundle for the connection details ("Oversize events", in the facilitator's People sheet under Connection details), and refuses every growing command (as `boardFull` or `meetingFullSize`, as if the board were over the cap) until a full refresh fits again. Changes that don't grow the board are still applied. A bundle that doesn't fit sets the signal; only a full refresh that fits clears it, because a change bundle may leave out entries that a full one carries. The meter keeps boards well inside the limit, so this should never happen.

**Frames are capped before parsing.** On either path, a frame over 48 KB is dropped before anything unseals or parses it: a relay event's content, a direct message's bytes, and a protocol 1 plaintext. A deflated protocol 2 plaintext is capped when it is inflated.

**The hard caps stay as outer bounds:** 280 characters per topic, 60 topics, 60 attendees, 60-character names and an 80-character meeting name.

**Two fixtures, two tests:**
- **Realistic.** 30 English topics of 50 to 110 characters (80 on average), 15 people with 12-character names, and every entry, each person with three dots, three acks and three rejects. The meter's bound is **14.1 KB** (14,149 bytes). The test asserts the bound stays under 16 KB, so typical meetings never meet the cap.
- **Adversarial.** Seeded with mulberry32 (seed `20261006`), every character is drawn at random, cycling through CJK ideographs (U+4E00–U+9FFF, 3 bytes in UTF-8), emoji (U+1F300–U+1FAFF, 4 bytes), CJK Extension B (U+20000–U+2A6DF, 4 bytes) and CJK again. It is random rather than repeated phrases, so deflate can't shrink it much. Topics are 280 characters, names 60 and the meeting name 80, and every entry is at its largest. The test builds the board through commands and asserts that the cap refuses a command before any full refresh passes 44 KB, that no event ever passes 48 KB, and that a refused command leaves the board and its `seq` unchanged.

**The measured arithmetic** (adversarial fixture, raw items as described above):

| Part | Size (the meter's bound) |
| --- | --- |
| 60 attendees with 60-character names of four-byte characters, no topics, every entry | 54.9 KB (54,895 B): over the cap, so the cap stops joins before 60 when names are that long |
| 60 attendees with 16-character ASCII names, no topics | 42.2 KB (42,156 B): inside the cap |
| 15 such people (adversarial), 10 topics of 280 such characters | 26.8 KB (26,803 B) |
| 15 such people, 20 topics | 36.4 KB (36,433 B) |
| 30 such people, 20 topics | 49.6 KB (49,602 B): over the cap, so fewer than 20 fit |
| Capacity with 10-character names and 60-character topics | 60 people and 60 topics: 43.7 KB; 30 people and 60 topics: 23.8 KB |

The meter is an upper bound, not the real size: every entry carries three tabs' acks and rejects and a refused join, with random stand-ins that deflate as badly as real IDs, 24 bytes of slack for each entry beyond the one it deflates, plus a margin of 2 % and 256 bytes.

## What the host sends, and when

### Saving, then sending

- **Views carry the last saved state.** After a command or tick changes the board, the host saves the board record (state, ack table and pending rejects together) and only then makes the new state the one its views are built from.
- **A failed save** keeps the change in the host's memory but sends nothing built from it: participants keep seeing the last saved state, and no new ack or reject goes out. The facilitator sees the save-failure banner. The host tries the save again on the next change and the next refresh; once one succeeds, everything since goes out together.
- **Presence-only flushes** (someone came online or went offline) need no save.

### Coalescing and the send budget

- **Coalescing.** After a change, the host flushes at most every **150 ms**, with a leading edge: the first change after a quiet period goes out at once, and later changes in the window wait for its end.
- **Views are built at send time,** from the last saved state at the moment the event goes out, not when the flush was scheduled. Intermediate states are skipped, never queued.
- **A flush** sends a direct `snapshot` to every peer whose reply path is direct, and one relay `bundle`.
- **The relay budget.** All the host's relay output goes through one budget of **2 events a second per relay**: at least 500 ms between host relay events. A bundle that is due sooner waits for its slot (a trailing send), and only the latest one goes out. Nothing bypasses the budget. The relay transport's own send budget (below) sits under this one and never holds the host back in steady state (2 a second against 2.86), and while a relay is down or out of budget a newer bundle replaces a held one instead of queueing behind it. The host sends no other relay events: bundles act as its transport heartbeat, and it answers no pings on the relay. The one exception is the host's refresh on a resume: the host's overdue timers run just before its visibility event, so a bundle may have gone out in the same instant to a socket that was dead (it is lost, or, if the transport held it, dropped on resume), and the 500 ms gap would delay the first bundle that can arrive. The resume clears the gap, drops a bundle waiting for its slot and sends its full refresh at once. The Retry button resumes too, on a page that may have a live socket, so there two bundles can leave less than 500 ms apart; the transport's own per-relay budget (a burst of 5, then one event every 350 ms) still bounds them.
- **Priority.** Bundles come first. Version replies (see Protocol version) are sent only in a slot no bundle needs, and are the first thing dropped when the budget is tight. A version reply that is refused (no spare slot, or a one-off limit) tries once more 500 ms later, through the same limits, because a hello every 5 s from a tab on another version can keep landing just after the 5 s refresh; refused again, it is dropped, not queued.
- **Full refreshes.** With or without changes, the host publishes a full refresh every **5 s**: a bundle with every entry, and a snapshot to every direct peer. If a change's bundle is due within the same slot, that bundle is the full refresh. This is 0.2 events a second with nothing happening, and it updates presence, repairs any loss and tells participants the host is alive.
- **Relay replies are counted.** `OK false` and `NOTICE` replies from each relay are counted in each relay's health (`RelayHealth`, which both sessions report as it changes), for the host's connection details. The facilitator's People sheet shows them under Connection details (see [mvp-screens.md](mvp-screens.md)); the browser battery prints them, with each relay's held and dropped events, when the ten-person burst test fails.
- **The scheduler is injectable**, so session tests run deterministically with a fake clock.

### Reply paths

The host records, for each transport peer, which path its last message arrived on. A peer's **reply path** is direct if its last message came direct and the direct path has carried a message from it in the last 10 s; otherwise it is the relay. Direct snapshots and pongs go only to peers whose reply path is direct. A failed direct send (a rejected Trystero send) marks that peer's direct path down, so it falls back to the relay; bundles reach it anyway.

### Accepting views

A participant accepts a `snapshot` or `bundle` only if every check passes:
1. it is signed by the host key in the share link (`h`), and names the meeting's `boardId` (a snapshot through `state.boardId`);
2. `host` equals the transport peer it arrived from, so a copy forwarded by anyone else is ignored;
3. it is newer: a higher `epoch`; or the same `epoch` and a higher `seq`; or the same `epoch` and `seq` and a higher `hostNow` than the last accepted view. Equal `seq` happens because presence, acks and rejects change without changing the board;
4. for a snapshot, `you` is the participant's own ID;
5. for a bundle, the participant has a usable entry: either the bundle holds an item that opens, verifies against `h`, names the participant as `you` and names the bundle's `epoch`, `seq` and `host`; or the participant already holds an entry for this `epoch` that arrived in a bundle whose `seq` is at least this bundle's `refreshSeq`. An entry from before the last refresh is never combined with a newer `shared`.

Only an accepted view can change which peer the participant treats as the host, so replaying an old one can't hijack anyone. Within an epoch, a participant combines the newest `shared` with its newest usable entry.

The participant fills in a default for any `ViewState` field that is missing (for example `phase: 'topics'`, `timer: null`, `vote: null`, `rehearsal: false`), so a view from an older or newer host still renders.

## Joining

- A `hello` from someone new, or with a new name, becomes a `join` command applied by the host. A hello that changes nothing doesn't change `seq`; the host marks that person's entry as changed so they get a view in the next flush.
- **A refused join** (`emptyName`, `meetingFull` or `meetingFullSize`) has no tab to acknowledge, so the host answers it with a view for that person: the normal `shared` part, and a personal entry whose `joinRefused` is the message key. It goes in the next flush and in refreshes for the next 30 s. If the hello came over the direct path, it also goes as a direct snapshot at once and in every full refresh until those 30 s are up, to a peer that has no record. Each of those snapshots is a one-off reply charged to the refused-join budget (see below): a refresh sends at most 5, the newest refusals first, and at most one per peer and signer every 5 s. So someone holding the room key who keeps several newer refusals alive can keep a real refused joiner from getting a direct answer; that joiner sees "connecting" rather than the refusal. This is bounded by the 64-entry list and the 30 s window, and is no worse than before. A refused joiner is never heard: it isn't online, isn't in presence and gets no other views. The same refused hello again, with the same name from someone who isn't an attendee, runs no new join and is answered, on the path it came on, at most every 5 s, until the 30 s are up; hellos sent at once run the join only once. A different name runs the join afresh, and so does a `meetingFullSize` refusal after those 5 s, since a smaller board can clear it (an empty name or a full meeting can't clear, and is answered from memory). A refusal the 64-entry cap forgot early runs as a new one, so the joiner is answered again, but its direct snapshot is still held to the one-off limit. A bundle carries at most three refused joiners' entries, the latest, and when a bundle has to be trimmed to fit the relay limit those entries go only after the direct-path people's and never before an attendee's (see The ceiling), so a relay-only joiner still sees the refusal unless the bundle with every relay-only attendee's entry plus the refusal does not fit (a known limit; see The ceiling). The host remembers at most 64 refused joiners, the latest, and forgets each when its 30 s are up, so signers minted with the room key can't grow the list; one that was forgotten early says hello again. The join screen shows the refusal, and "Take part" tries again, perhaps under another name (see [mvp-screens.md](mvp-screens.md)). The page sends someone back to the join form only if they are not an attendee: an attendee whose rename was refused keeps the board, their name and their views. After a retry the page ignores a refusal in any view built less than 2 s (host clock) after the retry, because such a view may predate the host handling the new hello; the next view carries the answer. An ignored refusal does not count as a refusal for the prompted hellos, which go on in case the retry's hello was lost. The 2 s cut-off is on the host's clock, taken from the newest view's host time plus the time since that view arrived by the participant's own wall clock, so a forward step of that clock delays a genuine refusal by the step, no longer. Until the host lists someone as an attendee, their page shows "connecting", not the board.

## Commands

### In order, per tab

- `clientSeq` starts at **1** for each tab (`sid`), and a new `sid` is made on every page load.
- A `cmd` is **well formed** if `boardId`, `clientSeq`, `sid` and `epoch` are present and valid. A frame that isn't well formed, or whose `boardId` isn't this meeting's, is dropped without a trace.
- The host applies each tab's commands strictly in `clientSeq` order, starting from 1 for a tab it hasn't seen. For each `(person, sid)` it keeps `ack`, the highest `clientSeq` applied with no gaps:
  - `clientSeq <= ack`: a duplicate. It is not applied again, but the person's entry is marked changed so the ack goes out in the next flush. A duplicate doesn't count as activity (`lastCommandAt` stays), so a replay can't keep a tab alive or decide which tab is dropped. The host lists it in the next views from a short-lived note in memory, made once per 10 s for a tab however many copies arrive.
  - `clientSeq == ack + 1`: applied, then any buffered commands that now follow without a gap.
  - `ack + 1 < clientSeq <= ack + 64`: buffered in memory until the gap is filled. A gap still open three resend cycles after it appeared (11 s: the participant resends everything it hasn't had acknowledged every 3 s for the first three resends, and then at a longer gap while the host is alive) can never fill: the host's table is behind the participant's, after a restore or a lost save. The tab is refused with `staleTab` and its buffer dropped, whether or not anything more arrives, so one or two lost resends never end a tab. The host then remembers that tab's gap as refused (an exact list: 20 tabs per person, across 600 people, a person's own oldest forgotten first; one person's refusals never push out another's), so a copy of one of its held-back commands can't open the gap again; its missing command, if it ever comes, ends that. This covers an unknown `sid` whose first command isn't 1. A person has at most 5 open gaps, and the host 300 in all; a gap past that is dropped until one closes.
  - Beyond the 64-command window: dropped.
- A command whose `epoch` isn't the host's current epoch is dropped. The participant resends it with the new epoch once it hears from the new host session.
- **Only attendees have tabs.** A command from someone who isn't an attendee is refused with `notAttendee` in a one-off view sent straight back to the peer that sent it. It makes no tab entry and nothing is saved, so signers minted with the room key can't fill the table. A participant treats that refusal as "not yet": the command stays pending, nothing is shown, and it is sent again once a view lists them as an attendee.
- **One-off replies are limited.** A reply the host sends because one message arrived, with nothing saved (a `notAttendee` refusal, a refused join's direct snapshot, a direct snapshot answering a hello whose clock is out, a version reply), goes at most once per kind, peer and signer every 5 s, and on the relay only in a slot no bundle needs. Each kind has its own cap of 5 every 5 s, so a flood of one kind can't use up another's; a reply to an attendee with a bound record doesn't count against it. One past that is dropped; its sender sends again. Pongs go only to known peers, on the direct path.
- **Commands the host can't apply are refused, not dropped.** A well-formed `cmd` whose inner command is unknown, malformed or a `join` is refused with `badCommand`. It advances the ack like any refusal, so it can never block that tab.

### Acks and rejects

- **A refused command still counts as applied**, so it moves the ack on. The host keeps only the **last reject per tab**, `{clientSeq, key}`, until that tab's next command is applied or refused.
- **Acks cover the person's tabs.** Each person's view carries `acks` and pending `rejects` for their tabs, so a person with two tabs open sees both acknowledged. To keep entries small, a view lists at most the **three** tabs of that person with the most recent command; a tab that isn't listed gets listed again when it sends a new command, or resends one already applied (at most once per 10 s), because that makes it the most recent. The tab with the newest command always has a slot. Known limit: because a tab is listed at most once per 10 s, a lossy tab that is not the live one can't bring its ack back by resending while four or more other old tabs of the same person are being replayed by someone watching the relay; this is bounded (the outbox gives up after at most two minutes and shows that the send failed), and the live tab is never affected.
- **Acks only after the save.** The ack table, with the pending rejects, is saved in the same write as the board, and an ack or reject goes out only in a view built after that write resolved.
- **Where the table lives.** In `BoardRecord.tabs`, beside `state` and outside `BoardState`: `{personId: {watermark, tabs: {sid: {ack, lastCommandAt, reject?}}}}`. The backup file (Back up meeting file, which includes the keys) keeps it, so a restored meeting still recognises duplicates. The plain export leaves it out. A backup file is checked before it is used: its state must name the same meeting as the record (a mismatch would make every hello and command drop), its `timerSound` must be a known sound or the file is refused. The `persistence` note (see mvp-screens.md banner 6) belongs to the browser that made it: neither a backup nor a plain export carries it, and an import drops it if a file has one. The table that is kept is the one parsed and brought within the bounds below, never the raw one from the file.
- **After a host reload,** the saved acks still recognise duplicates, so a command resent across the reload is never applied twice.

### Pruning

- A tab is pruned after **24 hours with no command** from it.
- **Bounds.** A person has at most **5** tabs (`MAX_TABS_PER_PERSON`). A sixth drops that person's least recently active tab. The whole table holds at most **300** entries (5 × 60), counting a person with no tabs left as one. Attendees alone never reach it. If it is ever full, a new tab is refused with `tooManyTabs`; nobody else's tab is dropped to make room. A person whose last tab went more than 24 hours ago is forgotten, watermark and all.
- When it prunes a tab, the host raises that person's **watermark** to the tab's creation time, if that is later, but never past the host's own clock, so a device whose clock runs ahead can't lock out its own later tabs. When it drops a tab, it raises it only to the creation time less 10 minutes, so a device whose clock runs up to 10 minutes slow can still reload after a drop.
- **Nothing that left comes back.** Every `sid` that leaves the table during a host session (dropped, pruned, or forgotten with its person) goes into an in-memory filter for that person (a 2 KiB Bloom filter; past 600 people they share one larger filter). A command from a `sid` the filter holds is refused with `staleTab`, even if its person has no entry any more. A false positive only refuses a new tab, which a reload replaces. A command from an earlier host session carries an earlier epoch and is dropped anyway.
- **A dropped tab** is remembered by its `sid`, with the person's last ten. Its next command is refused with `tooManyTabs`: "This meeting was opened in too many tabs. Reload this page". Its old commands can never be applied again.
- **A loaded table** (a reload, a restored backup) with more than 3,000 raw entries (10 × 300) is refused outright, before any of it is checked: a backup file carrying one isn't imported, and a stored one loads with an empty table. Otherwise it is brought within these bounds: each person's extra tabs are dropped as above, in one pass, then, if it is still over 300, the people least recently active are forgotten (one sort). That is safe only at load, under a new epoch. A reject above its tab's ack is left out.
- The host forgets a refused tab's reject after 5 minutes.
- A command from a `sid` the host doesn't know, whose creation time is at or before the person's watermark, is **refused**: the host can't tell which of its commands were already applied. It is not applied, no ack entry is made for it, and the person's next views carry a reject for that `sid` with the key `staleTab` until that tab sends again. The participant shows "This page has been away too long. Reload it to carry on." A sid with a later creation time is a new tab and starts from 1 as usual.

### Retries, on the participant

- A participant keeps every command until it is acknowledged.
- **It sends nothing until it is an attendee.** Until a view lists it as an attendee, its commands wait, in order; once one does, it sends them all from `clientSeq` 1. If a later view doesn't list it (or a `notAttendee` refusal arrives with one), it holds again, and resends everything pending from the oldest when it is listed again. A hold doesn't count towards the retry count or the two minutes.
- If the oldest unacknowledged command has had no ack **3 s** after it was last sent, the participant resends **all** unacknowledged commands, in order from the oldest. It does this three times at 3 s. After that it keeps resending only while the host is known to be alive (the participant has heard from it within the 20 s that make a host offline: a busy host is slow, not gone), with the gap doubling: **6, 12, 24 s, then every 30 s**, and stops when nothing has been acknowledged for **2 minutes** counted from the first send, or from the latest ack that moved things on, Retry or release. If the host is judged offline it stops at the next timer, which is later than before: the host is judged offline after 20 s of silence, then up to one gap (up to 30 s) passes, so about 27 s after a send if it dies just after one, up to about 50 s if it dies late (it was 12 s). If only the person's own sends are lost while they still hear the host, "didn't reach" shows after 2 minutes instead of 12 s. A new command while the resends have backed off gets its three 3 s resends again (the host's gap rule assumes them), the 2 minutes unchanged; the relay transport keeps a held copy of a command (does not treat it as expendable) once the next resend is more than 3 s away. A timer that fires long after it was due (a locked phone) resends everything once and counts afresh instead of giving up. No wire change: a resend is the same command, sealed the same way, and the host already ignores copies (by tab and count); the back-off is what keeps copies from adding to a host that is busy.
- When the participant hears from a new host epoch, it seals its unacknowledged commands again with the new epoch, keeping their `clientSeq`.
- **Giving up.** When the resends stop (the host offline after the third resend, or two minutes without an ack), the participant shows "Your last change didn't reach the facilitator." with Retry. Retry resends from the oldest unacknowledged command and starts the count again, so a gap can never block a tab for good.
- **Showing a reject.** When the participant's view has a reject for its own `sid` with a `clientSeq` it hasn't shown yet, it shows that message once.
- While the host is offline the board is read-only, so no new commands are made; unacknowledged ones keep their retry schedule.

## Pings, clocks and liveness

### Pings

- Participants ping every **5 s** while they consider the host online, on the direct path if it is proven and on the relay otherwise. Pings are the participant's own events, so they cost the host's budget nothing.
- The host records every accepted ping, and every command that applies (the tab's next command), as "heard from" for presence (`online` means heard from in the last 15 s). A command held for its turn, a duplicate, a stale or evicted one and a refused one are answered or kept but never count, so an old command delivered again keeps nobody online; a tab that resends because its acks were lost stays online through its pings. A hello makes a record but never counts as heard: a new record counts only once an accepted ping, or a command that applies, comes from it. A joiner pings as soon as it accepts its first view, so it shows online almost at once; one that never gets a view never shows online, and its record expires after 60 s.
- **A ping counts once.** The host accepts a ping only from a peer it has a record for under that signer, only if its `n` is higher than the last it accepted from that signer and `sid`, and only if its `at` is within **60 s** of the host's clock. Only then does it mark the person heard. So a copy of a ping keeps nobody online. The last `n` per signer and tab is kept in memory until a copy of that ping could no longer be fresh (60 s after the later of its `at` and the time it arrived; an entry is never shortened by a later one), whether or not the signer still has a record. Bounds: attendees have their own pool (at most 5 tabs each, with no count limit beyond the board's attendees, so an imported board over the usual limit fits too), and anyone else has a separate pool of 300 that refuses new entries when full instead of evicting. Past five tabs for one person, the sixth tab's count pushes out the least recently used tab's count, so a still-fresh last hello or ping from that tab could be accepted once more (bounded by 60 s): a known limit. After a host restart the memory is empty, so a copy captured in the last 60 s can be accepted once. A participant counts its pings from 1 for each page load, and each ping's `t0` is later than the one before it.
- **A hello counts once, and only fresh.** The host handles a protocol 2 hello (a join, a rename, a new record) only if it names its tab, `n` is higher than the last hello accepted from that signer and tab (a refused one counts too), and `at` is within 60 s of the host's clock. The counts are kept like the ping counts, in the same two pools: a signer that is not yet an attendee is in the second pool, and when that pool is full (a flood of minted signers) a new stranger's hello is dropped without a reply and the newcomer stays on "connecting". A held entry is refreshed without the pool-full check and lasts up to about 120 s, so someone with the room key who keeps up about 300 signed hellos per two minutes from about 60 minted signers can keep that pool shut for as long as they keep sending; someone who only watches the relay can't, because that needs signing. That is no worse than the same person filling the meeting. An attendee's counts are never displaced by it (the attendees' pool has no count limit of its own, only 5 tabs each). Anything else, a copy of an old hello included, changes nothing at all: no join, no rename, no record. A genuine page's hellos each carry the next count, and the second copy of one hello (sent on both paths) is simply not newer. A page whose clock is far out has its first hello refused. Over the relay it then learns the host's time from a bundle (at most about 5 s). Over a direct connection the host answers the refused hello once, with the shared view as for a refused joiner (one per peer and signer every 5 s, under its own cap), and only if the hello came direct: the transport vouches for the peer, so a copy of a hello cannot draw an answer for someone else, and a hello on the relay gets no answer. The answer changes nothing on the host: no join, no count, no record. The page takes the host's time from that snapshot as it does from a bundle header, only from a newer snapshot over the direct path (see the clock offset section), and says hello again with a fresh `at`. A page more than 60 s out is therefore admitted with its relays down, as long as it has a direct connection; a page with neither relay nor direct connection cannot join at all. While it does not yet know the host, a page sends each hello to every direct connection as well as to the relay, and only the host answers; any page with its relays down, whatever its clock, now joins this way (before, it sent nothing direct until it knew the host, so it never joined). The cost: every new direct connection prompts a hello, so while the host is absent a mesh of n pages sends about n hellos per page as it forms, each to every direct peer; they are small and other participants drop them unread. The answer has a cap of its own, five per 5 s for anyone who is not a bound attendee, and it is not sent to a tab that already has a live record (its own views are better). That cap is a limit: someone with the room key who floods stale hellos from minted signers can use it up and leave a far-out-clock joiner on "connecting" for as long as the flood lasts, no worse than the same person filling the refused-join cap. A stale hello over a direct connection is answered even when the stranger pool is full, since the answer needs no pool entry. A new host session (a newer epoch, or another host peer) replaces what the page learned of the old host's clock and clears the retry point that hides refusals older than Take part, so a host whose clock is behind the old one's is joined, not refused. The host compares `at` with its own wall clock, so a step of that clock back by more than 60 s makes pings and hellos wait until the clock catches up or the host reloads.
- **The host answers pings only over the direct path**, with a `pong`. A participant accepts a pong only from its host peer, over the direct path, for a `t0` it sent and hasn't had answered, once. It keeps at most 8 unanswered `t0`s.
- **Hearing from the host.** Only an accepted view (signed by `h`, and newer under Accepting views) or a pong for an outstanding `t0` counts as hearing from the host. Duplicates and replays never keep the host online.

### The clock offset

The host's clock is the source of truth for timers. Each participant estimates `offset` so that host time is local time plus offset.
- **Direct path:** from each pong, `offset = t1 − (t0 + t3) / 2`, where `t3` is the local receive time. The participant keeps the last 8 samples and uses the one with the shortest round trip.
- **Relay path:** each bundle carries `hostNow`, which counts only from an accepted bundle: one that is newer under Accepting views, so a replayed bundle can't move the offset. Relay pings carry the frame flag `e: 1`. The relay transport normally drops events its own page published, but passes `e: 1` frames back to the session as echoes, and the session records **relay latency** as the time from publishing to the echo. Then `offset = hostNow − receivedAt + relayLatency / 2`. The participant keeps the last 8 bundles and the last 8 echoes, and uses the largest `hostNow − receivedAt` plus half the smallest echo latency.
- The participant uses the direct estimate when it has had a pong in the last 30 s, and the relay estimate otherwise.
- **Before the first reading:** a page's `at` for a ping or hello comes from the clock once it has a reading, and before that from the largest `hostNow − receivedAt` of the newest verified bundle headers or of a snapshot from the host peer that arrived over the direct path and is newer than the last view accepted. That value feeds only `at`, never the offset. A relay frame's sender is not authenticated, so a snapshot that arrives by relay never feeds it; a replayed, older or duplicate snapshot is not newer and feeds nothing.
- **Testable bound.** A session test with an injected clock, a host clock 7 s ahead of the participant's, and a simulated relay that delays each event by a random 50 to 600 ms in each direction asserts that the relay estimate is within **500 ms** of the true offset after four bundles and four echoes. The same test with the direct path, delaying each message by a random 5 to 100 ms (a data channel's delay, not a relay's), asserts 100 ms.

### Offline thresholds

| Who | Rule |
| --- | --- |
| Participant, about the host | The host is offline after **20 s** with no accepted host message on any path (four refreshes). A transport saying the host's peer left (a relay's sweep after a freeze, a dropped WebRTC connection) changes nothing |
| Participant, about the direct path | The direct path is down after **15 s** with no host message over it; the participant falls back to the relay |
| Host, about a participant | Offline (out of `online`) after **15 s** without an accepted ping or a command that applies from them |
| Host, about a peer's direct path | Its reply path falls back to the relay after **10 s** of direct silence |
| Anyone, about the relays | With no relay socket open for **10 s**, every device shows "Can't reach the meeting network. Check your connection." The direct path keeps working where it exists |

## Reconnecting

### Participant

- **Hello.** Until it has a host, a participant says hello, then again after 2, 4 and 8 s, then every 15 s. The back-off resets when the page becomes visible and whenever it hears from the host.
- **On becoming visible** (`visibilitychange` to visible, or `pageshow`), it sends one hello as a relay broadcast, whatever the transport's peer list says, and another directly to the known host peer. It treats the direct path as unproven until a host message arrives over it.
- **Proven direct path.** A participant sends over the direct path only after it has received a host message over it; until then everything goes over the relay. The one exception proves the path: while the host's direct connection is up but unproven (it usually connects after the first relay view), the participant sends a direct ping every 2 s, with no relay fallback, and the host's pong over that path proves it.
- **Relay pacing.** A participant's commands on the relay keep to a burst of 4, then one every 400 ms, inside public relays' limits (a burst of 6, then 3 a second), so resending many commands is never refused. The relay transport adds a limit of its own under that, see "The transport's send budget" below. Commands queued for the relay are sent in order; one the host has acknowledged while it waited is skipped, so a slow queue never sends what is already done. At most one resend of the pending commands waits in the queue: a resend that falls due while the previous one is still queued is dropped (the next one sends the whole pending set), so fresh commands wait behind one resend at most, never a backlog of them. The resends stay bounded by the retry rule above (three at 3 s, then back-off for at most two minutes).
- **After the meeting has ended,** a participant whose host goes away keeps the last ended view on screen and shows no connection error. It says hello every 45 s and on becoming visible, so a reopened meeting comes back to life.

### Host

- **On becoming visible,** the host reconnects to the relays and resubscribes, sends a full refresh (bundle and direct snapshots), runs `tick`, and requests the wake lock again.
- **Epochs.** Whenever the host resumes from storage, after a reload or an import, it sets `epoch = max(saved epoch + 1, Date.now())` and saves it before sending anything. Its first view then beats anything older, even if the saved epoch was lost or came from an older backup. The stored epoch is never lowered.
- **Direct path after a resume.** Trystero forms a direct connection only when a peer announces itself on the relays: a few times in the first 2 s after joining the direct room, then once a minute. In practice it does not announce again when a connection drops (its option to do so does not apply to the shared connections every direct link uses), so a direct path lost while a page was hidden would come back only at the next minute's announcement (45 to 60 s in tests), and the relay would carry everything until then. So on becoming visible, a page rejoins the direct room when a link it cares about was lost in the lock. A participant cares only about its link to the host it last knew; the host cares about every participant's link. A link counts as lost when its connection has failed or closed at the resume, or when its peer was in the direct room as the page turned hidden (or joined it while the page was hidden) and at the resume is gone from the room or its connection has failed or closed, however its loss was reported: a lock's ICE timeout, the other page closing its connections (as closing or reloading its tab does), or the other page leaving the room. A connection that is only disconnected at the resume does not count: ICE may recover it (a short lock, a Wi-Fi blip), and Trystero gives it 5 s to before it closes it and reports the peer gone, which the 30 s watch below then counts. Only a resume of a page that was hidden starts that watch: the Retry button resumes a visible page, so a link only disconnected then is not watched, and once Trystero closes it the direct path waits for the minute's announcement. A page that starts hidden (opened in a background tab) counts as hidden from the start. A participant counts a lost link only while its link to the host is down at the resume, and then whichever link it was: a host that reloaded while the participant's phone was locked comes back under a new peer ID, which the participant may already have heard of. Otherwise a peer that leaves while the page is visible makes it rejoin only within the 30 s watch below, and having no direct link at all never does: rejoins stay rare. To rejoin, the page closes the connections that have failed or closed (not one that is only disconnected), leaves the room (if Trystero's leave fails, it closes every connection and tries once more; if that fails too, it stays in the old room until a reload; a room it cannot leave once its meeting has been left, even mid-rejoin, keeps announcing on the relays until the page reloads, and the page logs a warning saying so), and joins again through fresh signalling clients: Trystero keeps one client per relay URL for the life of the page, and a client whose announcement found its socket closed, as happens around a resume, sends no announcement for a minute or more. So each rejoin adds `?rejoin=n` to the relay URLs, which relays ignore, and Trystero makes new clients, which announce as soon as their sockets open. Trystero sets up its clients only for a join made while the tab has no direct room (a room being left counts until its leave finishes, about 100 ms later, and one Trystero could not leave counts for good), and gives every room joined meanwhile those same clients, whatever URLs it asks for. The URLs a rejoin has finished with are retired for the whole page: no join asks for them again (another meeting opened from Home, say, asks for fresh marked URLs), though a room joined while another is open or being left gets that room's clients, retired or not; a marked URL is retired when its meeting is left. A transport that starts while the same meeting's room is still being left (Trystero would hand it the room being left) joins once that leave is done. The page closes the socket of each retired client once no room uses it (one may be half-open after a lock), and keeps doing so every 5 s, since an old client may still open a new socket from a retry its socket's earlier close started: for 65 s after a rejoin, and for 65 s more each time it finds a socket reopened or not yet closed, up to 3 minutes. A client that waits for the browser to come back online opens its socket once it is, so the page sweeps again then. The fresh announcements bring the direct path back within seconds; messages go by relay until then. If joining again fails, the page has no direct room, uses the relay, and tries again at its next resume. A page that was hidden and finds its links up instead watches for 30 s and rejoins once if one it cares about goes down in that time: a real lock ends a connection by ICE timeout, some seconds after the page is back. A rejoin starts no watch, but may be followed by more rejoins for a link it lost (below). That left a gap: a resume that rejoins for one lost link while another link it cares about is only disconnected (the host back from a lock with one participant's connection closed and another's still recovering, say). Trystero gives the new room every shared connection that is not failed or closed, but the new room lists a peer, and reports it joined, only once its own handshake with that peer over the connection's data channel has finished, which a disconnected connection cannot do unless it recovers within the handshake's 10 s. So the new room never lists that participant, and when Trystero closes the connection, up to 5 s after it disconnected, no room reports the peer gone. The later rejoins below now bring that link back. In the watch, a peer reported gone with its connection still up counts as having left on purpose (its page rejoined, say), so pages do not set each other off; a link the other page closed, whose loss is reported only after the resume, looks the same and waits for the minute's announcement. Costs and limits: the resume runs on every return to the tab, so on a desktop a tab switch rejoins if a link went down while the tab was in the background (a participant's phone locking, for the host); a rejoin leaves the room for the page's healthy direct links too: Trystero may keep such a connection, which it shares between rooms, and hand it to the new room, or the link forms again with the rest (the browser battery checks that the host's survives or forms again within 15 s and that the host's new room lists that participant, and logs which); the other pages see it leave: a visible one does not rejoin in turn, but a hidden one counts the link as lost and rejoins at its resume if the link is not back by then (a participant only while its link to the host is down), as when two phones are locked at once; a participant whose link to the host is down at a resume also rejoins for a link to another participant lost in the lock; a direct connection lost while the page stays visible, or lost during a handshake that never finished, still waits for the minute's announcement, except a participant's link to the host: a participant whose page is visible and whose link to the host is reported gone rejoins once, and never within a minute of any rejoin of that page, a resume's or a watch's included: at once if the connection is not connected, else (the host's page rejoined, or the host closed its end and Trystero has reported it gone before ICE gave up) if the host is still not in the room 8 s later. This is the case where the host's page rejoined after losing that one link: the participant's old connection still read live, so Trystero ignored the host's announcements (it ignores a peer it holds a live connection to), and it closed that connection about 5 s later, after those announcements had stopped. In some CI rounds Trystero reported the host gone while the connection still read connected (the data channel closed, the connection not until ICE gave up), so the first form of the rule, which wanted a connection not connected, never rejoined and the link stayed down (run 30770, rounds 9 and 13: the participant's rejoin count stayed 0, the host's count of connections stayed 1 for 30 s). The participant's own announcements then bring the link back in seconds. A host whose page rejoined leaves its connections up and its new room takes them back within seconds, so a participant that finds the host back within the 8 s does not rejoin in turn, and no other page rejoins for a visible link loss. Costs and limits: when the facilitator's machine sleeps or loses its network for more than about 5 s, every visible participant rejoins at the same moment, so the relays see N announcement bursts together (no jitter for now); and the rule helps only when the host's side closes first: if the participant's side closes first while the host's side still reads connected (a symmetric blip), the host ignores the participant's fresh announcements and the link waits for the minute's announcement, as before. A link that does not come back after a rejoin. Two causes were found in CI (40 rounds of a resume in a meeting over a minute old, the facilitator's page locked for 10 s: 7 failed, none with a link 20 s later). (1) A participant that rejoins for its link to the host while the host's page is still locked holds a connection to it that is disconnected, not yet failed, when it rejoins. Its room had already reported the host gone, so the page's own list of the room's connections no longer held it, and the rejoin did not close it; but Trystero kept it as a shared connection, gave it to the new room, ran the handshake over it, and ignored the host's announcements for as long as it held it (about 10 s more, until ICE failed it), after which nothing announced again for a minute (5 of 7 failures). So a rejoin now closes the connection of every peer its room reported gone and has not reported back, unless that connection is still connected and the peer left under 5 s ago (its page most likely rejoined, and its new room takes the connection back; one left longer is closed all the same). (2) The other page's old room is still leaving (Trystero's `leave()` waits 99 ms) when its page resumes, and in that time it can make or answer an offer for the new room that its leave then abandons; Trystero ignores the new room's announcements while it holds that half-made connection, up to 23 s (2 of 7 failures). That cannot be stopped from outside the other page, and a retry 10 s on can still fall inside the 23 s that page holds the half-made connection, whichever page it is, so a page that rejoined for a link it lost, and has not had that peer back in the room 10 s after the rejoin finished (the page visible, the meeting not left), rejoins once more, and if the link is still missing 26 s after that (past the 23.333 s Trystero holds it, so the fresh announcements are answered) rejoins a last time; that one starts no other, so at most two extra rejoins follow a rejoin. A peer is waited for only if it was in the room, or left it within 2 minutes with a connection not failed or closed (a participant's host always counts); one that left with its connection down, as a closed tab or a reload does, does not, so the host does not rejoin again for people who have gone. Two pages' last rejoins could in principle fall together and make the half-made connection again, with nothing left to retry; that needs both pages to be missing the link at the end of their own 36 s, and the link then waits for the minute's announcement. Costs and limits: each extra rejoin costs the same few relay events and brief report of other peers gone as any rejoin, a link that takes more than 10 s to form after a rejoin on a slow network is torn down and made again, and a lock of the other page longer than 36 s is not waited out, so a participant's retries are spent before a host that resumes later (the minute's announcement or the host's own rejoin then brings the link); the page does not know why a link is missing, so it cannot tell a half-made connection from a peer that has not returned yet. Offers made after the first minute: Trystero keeps a pool of ready offers, and refreshes one more than 57 s old when it hands it out, by rolling the connection's offer back, restarting its ICE and making a new offer. In Chrome the rolled-back connection makes an offer with no transport in it (no ICE credentials, no candidates), so the other page had nothing to connect to and the connection failed after 23 s. Which of two pages makes the offer depends on the order of their peer IDs, the lower making it, so before the fix about half of the people who joined a meeting over a minute old stayed on the relay, and a resumed page got its direct connection back only if it made the offer or the other page's pool was under a minute old. Every connection Retrobrew gives Trystero is therefore built from a class (`src/transport/restart-offer.ts`) that does not roll an offer back and makes the ICE restart straight from the offer it holds, which Chrome gives new credentials and candidates; the restart offer is then not finished being set until its candidates are gathered, or 2 s have passed, so its SDP carries them (Trystero drops candidates found before it attaches a handler to a pooled connection). Known limit: if the STUN servers answer in more than 2 s (on a slow mobile network, say), the offer goes out with the host candidates only and the server-reflexive candidates found later are dropped, so a joiner that needs them has no direct path and stays on the relay. The browser battery covers a join over a minute after the host (`e2e/late-join.spec.ts`) and a resume in a meeting over a minute old (`e2e/recovery.spec.ts`).
- **Sockets.** nostr-tools gives up on a relay whose first connection fails, and closes its subscription, even though publishing still reconnects it. So both sides check their sockets every 5 s and reconnect a relay that is down, backing off from 5 s to 30 s. Each relay has its own subscription. A relay that comes back is subscribed to again at the next check, so at most once every 5 s and with no back-off. When a relay closes its own subscription (it errored, or sent a refusal while its socket stayed open) it is subscribed to again, backing off from 1 s to 30 s, and the back-off starts over once a subscription has stayed up for 30 s. After a resume they close every relay connection, one may be half-open, then connect and subscribe again.

### The transport's send budget

Under the pacers, the relay transport keeps what it sends to **one relay** to a burst of 5, then one event every 350 ms (about 2.86 a second), whoever sent it (commands, bundles, hellos, pings, heartbeats). That is inside public relays' limits (a burst of 6, then 3 a second) and a little faster than the participant's pacer (a burst of 4, then one every 400 ms), so the pings and hellos that pacer doesn't count fit in the gap. The budget runs on a monotonic clock; a wall-clock step changes nothing.

- **Held events.** An event for a relay that is down (its socket is closed, or the library dropped it after it had been up) or out of budget is held, in order, per relay, up to 20. When more wait, the oldest event that is not a command, or is a command that is expendable, is dropped first, so a fresh hello can displace such a command. A command is expendable once the host has acknowledged it (its held copy would only arrive as a duplicate) or while the outbox has a resend of it due within 3 s (one of the first three resends; once resends have backed off the next may be 30 s away, longer than the host's gap rule waits, so the copy is kept; that resend puts it back, if the host is online: a resend while the host is offline sends nothing, so a command dropped then needs the Retry the page offers when the outbox gives up). A command the outbox will not resend is kept, since its held copy may be the only one left: once the resends have backed off or the outbox has given up on it, and while the outbox is held (until a view lists the person as an attendee). Such commands are dropped, oldest first, only when every held event is one. If the queue is full of those, a fresh hello is the one dropped and the next goes at the hello back-off, and every drop is counted in the relay's health (`dropped`, beside `held`, the number waiting now, and `givenUp`). An event that makes held ones pointless takes the place of the first of them, and the others go: the host's bundles (each carries the latest state whole; a change bundle replaces held change bundles, never a held full refresh, since a participant without a usable entry would otherwise wait up to 5 s more for the next one; a full refresh replaces both), a participant's hellos (the host takes only the newest), the transport's heartbeats, and a resent command, which replaces only its own held copy, so it keeps its place ahead of later commands. A relay ping is never held: one that waited would time the wait, not the relay, and skew the clock offset. A copy of it that asks for no echo is held in its place (a newer copy replaces it), so the host still hears from the page: an accepted ping ends a new record's probation and keeps the person online. The next ping, with its echo, goes 5 s later. Nothing is sent to a down relay; held events go out, within the budget, once it is back, because nostr-tools would otherwise send everything published while a socket was connecting in one burst the moment it connected, and the relay refuses part of it. They go the moment the connection the transport asked for opens, or else at the relay's next wake-up (every second while it is down). Each relay has its own wake-up, so a relay that is down never delays an up one. A relay that has been down for 60 s is given up on for holding: its queue is emptied (counted as dropped), one warning is logged, and nothing more is held for it until it is back, which the transport notices when it publishes, at the 5 s socket check, or at a resume.
- **Signing held events.** An event is signed when it is published, so a relay that sends it at once and one that holds it within the same second send the same event and receivers drop the repeat by its ID. One held into a later second is signed again when it goes out, once for every relay that sends it in that second (the relays share the held event, so they send the same one): nostr-tools reconnects a subscription by itself asking only for events after the newest it had, by the second, so a receiver whose socket came back meanwhile would otherwise never see it. The cost: such an event can reach a receiver twice under two IDs, once from a relay that sent it at once; the protocol already ignores the repeat (a duplicate command is acknowledged and not applied again, a hello or bundle that is not newer changes nothing).
- **After a lock (resume).** Every relay is held for again, one given up on while the page was locked included, and the held events a fresh one replaces are dropped (not counted): hellos, heartbeats and bundles, since the page says hello again and the host sends a full refresh. Commands are kept. So the hello after an unlock waits behind the held commands only, never behind stale events.
- **Reconnecting.** While events wait for a down relay, the transport asks for it to be reconnected with the same back-off as the 5 s socket check (5 s, 10 s, 20 s, then 30 s). A relay that was up and has dropped is closed in the library first, so its own reconnect timer is cleared. A connection still being made is never closed: the first one, one a resume or a resubscription started (the transport notes when it asks for a relay that isn't connected), or any attempt younger than 4 s (the library gives up on one after 3 s). Closing it would let the library's timeout later forget its replacement and leave a socket open outside the pool; the transport only asks for the connection and joins the attempt in progress.
- **What a drop costs.** A command: nothing once the host has acknowledged it; otherwise the outbox resend, 3 s later (a held command that is not acknowledged is dropped only while a resend of it is still to come, or when 20 commands the outbox will not resend wait; if then dropped, Retry sends it again, or, for a held outbox, the release once a view lists the person as an attendee). A hello: the next hello. A ping: its echo, which is never held, is not sent to that relay, so that relay gives no latency sample for it; its held copy, if dropped too, costs the host hearing from the page until the next ping, 5 s later. A bundle: the next bundle (500 ms) or the full refresh (5 s). Nothing is kept for ever: memory per relay is bounded by 20 events.

### Targets

- The board updates within 5 s of a participant unlocking their phone.
- Participants are back within 5 s of the host unlocking theirs.
- While the host's phone is locked, nobody can change the board. A running timer keeps going on the host's clock, so a guest whose timer reaches 0:00 meanwhile sees "Time's up will show when the facilitator is back." and the time-up vote opens for everyone once the host is back. A guest's head count holds the guest alone, since only the host knows who is present. Participants see "The facilitator's device is offline", with the board still visible and read-only.

## Protocol version

- The current protocol version is **4**. A hello without `pv` names no version and gets the version reply.
- **Protocols 1, 2 and 3 are not supported.** Protocol 3 renamed the board's and the messages' fields and changed no layout or rule; protocol 4 added the `undoMoveOn` command, which a protocol 3 host would refuse as `badCommand`, so a tab on protocol 3 gets the version reply like any other mismatch. A tab running protocol 1 or 2 no longer gets the friendly reply below, and may show nothing useful: both sides should reload to the same version.
- **Saved boards and backups from before protocol 3 don't open.** The IndexedDB board store is version 2, keyed by `boardId`; when a version 1 store is found, its boards are dropped, not read. A backup or archive file is `{format: "retrobrew-board", version: 2}`; a `version: 1` file is refused on import with a message saying it was made by an older version of Retrobrew and can't be opened, so the person starts a new meeting. Why: Retrobrew had no release before protocol 3, so no one has such a board to keep, and nothing in the code reads the old format.
- Hellos are always sent in the protocol 1 plaintext layout (uncompressed, no prefix) with `pv` and `boardId` added, so that any host can read them.
- **A hello whose `pv` differs from the host's** (or that names no meeting) gets the version reply instead of a join: a `snapshot {epoch, seq, you, host, state}` in the plaintext layout of hellos, sent to that peer. It carries the host's current epoch and the correct `you` and `host`. Its `state` is a minimal board: `topics: []`, `timer: null`, the recipient as the only attendee, and `boardName` set to "This meeting was started with a different version of Retrobrew. Reload this page." The host sends it at most once per peer and signing key every 5 s, in a relay slot no bundle needs; a reply that gets no slot tries once more 500 ms later (see Priority), and ignores every other message from that peer. The record that says a peer is on another version is its own, per peer and signing key, and the host holds at most 64 of them at once, the oldest going first, so signers minted with the room key can't grow the table; these records never displace a protocol 4 record. A version reply counts for a participant only when it is newer than the last view it accepted and than the last version reply it accepted, so an older or replayed one never sets the version mismatch again. Presence lists only peers on this version, one entry per peer and person.
- **A participant that receives a version reply** shows the version mismatch screen (see [mvp-screens.md](mvp-screens.md)). If the reply's `boardName` is the sentence above, the host is newer and the participant should reload; otherwise the host is older, and the facilitator should reload.
- **A view clears the mismatch screen.** If an accepted view arrives later (the facilitator reloaded, for example), the participant leaves the mismatch screen and shows the board.

## Two facilitator pages

A meeting file holds the host's signing key, so opening it in a second browser starts a second page that signs as the same host. Neither page can take the meeting from the other, and nothing on the wire changes (protocol 4 is as it was). Each host page watches for what the other already sends: a view, or a relay bundle that verifies, signed with its own key but carrying a `host` (the sender's transport ID) that is not its own. A relay may keep and replay events, including those of this browser's own earlier page loads, so only a live message counts: one from a session at least as new as the page's own epoch (epochs rise with every start), or from an older one that arrived directly or whose `host` is heard again 4 s or more after it was first heard (a replay comes in one burst; a live host refreshes every 5 s). A page that sees one sets `otherBrowser`, which shows the facilitator banner in [mvp-screens.md](mvp-screens.md), and clears it when none has arrived for 90 s (the hosts refresh every 5 s). The warning is advice only: both pages go on running, and participants follow whichever host's epoch is newer. The same browser's second tab is handled by the lock, not by this.

## Signed messages carry their context

Every signed message names enough context that a copy replayed from elsewhere, forwarded by another peer, sent to another meeting or held over from an earlier host session is rejected.

| Message | Context it names | Receiver's check |
| --- | --- | --- |
| `hello` | `peer` (the sender's transport ID), `boardId`, `pv`, `sid`, `n`, `at` | The host ignores a hello for another meeting, whose `peer` isn't the transport peer it arrived from, that isn't newer than the last from that signer and tab, or whose `at` is more than 60 s from its clock |
| `cmd` | `boardId`, `peer`, `sid`, `epoch`, `clientSeq` | The host ignores another meeting, a `peer` that isn't the transport peer it arrived from, an earlier epoch and duplicates, and attributes the command to the signing key |
| `ping` | `boardId`, `peer`, `sid`, `n`, `at` | The host ignores a ping for another meeting, whose `peer` isn't the transport peer it arrived from, that isn't newer than the last from that signer and tab, or whose `at` is more than 60 s from its clock |
| `pong` | `t0` (the participant's own timestamp) | Accepted only from the host peer, over the direct path, once per outstanding `t0` |
| `snapshot` | `you`, `host`, `epoch`, `seq`, `hostNow`, `state.boardId` | Accepted only if it is for this participant and meeting, came from the peer it names as host, and is newer |
| `bundle` | `host`, `boardId`, `epoch`, `seq`, `refreshSeq`, `hostNow`, `itemsHash` | Accepted only if it is for this meeting, came from the peer it names as host, and is newer |
| `personal` | `you`, `host`, `epoch`, `seq` | Accepted only inside an accepted bundle with the same `host`, `epoch` and `seq`, and only for its `you` |
| Version reply | `you`, `host`, `epoch` | As a snapshot in the hellos' plaintext layout |

**The host takes nothing from a transport peer ID.** A frame's `from` says only where to send a reply and which of a signer's records the message belongs to. Records are kept per transport peer and signing key, so a message signed by someone else and sent as another person's peer never reaches that person's record, protocol version, reply path, presence, refusals, one-off reply limits, acknowledgements or role. All of those come from the signing key.

Also:
- **Only the host's key counts.** Participants ignore any host-side message not signed by `h`.
- **Commands are attributed to the signing key,** never to the transport peer.
- **A relay frame's `from` is only a claim.** The host keys what it knows of a peer (protocol version, reply path, presence) by transport peer and signing key. A message signed by someone else that names the same peer gets its own record and can never change that peer's.
- **A version reply** counts only if it is newer: not from a host session older than the one the participant follows, and not one seen before.

## Accepted gaps

These are stated here and in the landing page's FAQ.

- **The relay path uses the shared room key.** Everyone in the meeting holds that key, and every relay event reaches everyone in the room. A meeting member who records relay traffic can therefore:
  - open other people's personal entries in a bundle, which means seeing their dots while Show votes is off, and the vote totals in facilitators' entries;
  - work out who chose what in a time-up vote, from people's signed `voteToContinue` commands on the relay and from the changes between successive entries.

  Retrobrew never shows or stores who chose what, and never sends the `voters` list, but that is hygiene, not secrecy. Sealing each message to its recipient is post-MVP work. On the direct path each message goes only to its recipient.
- **Relays and STUN servers see metadata.** Public relays see IP addresses, timing and message sizes, never content. When a direct connection is set up, the STUN servers learn participants' IP addresses, and the facilitator's device and each participant's device learn each other's.
- **Participants always use the default relays.** A facilitator's edited relay list doesn't reach them.
- **Relay frame fields outside the seal are not authenticated.** Someone who sees the relay traffic (no room key needed) can resend a captured sealed frame, and can set its `from` to anything. What that can and can't do: a ping or hello is accepted once, only while its `at` is within 60 s of the host's clock, and never after a newer one from the same tab for as long as the host remembers that tab (60 s after its last, in memory, lost at a host restart: a copy captured in the last minute before a restart can be accepted once; stranger entries are refused rather than evicting when their pool is full); a copy of a command names its own peer, so under another `from` it is dropped, and a duplicate never counts as heard; only a ping or a command that applies makes anyone online, so a hello, a held-back command or a refused one never does; the host remembers a refused gap or tab refusal per person, so copies can't reopen or repeat it. Holding a ping back and delivering it later can make someone look online until its `at` is more than 60 s old. Signatures and the checks above stop anything more.
- **Votes are per device,** not per person, because there are no accounts.
- **While the host's device sleeps, nobody can change the board and the timer keeps running on the host's clock; time's up appears when the host is back.** The wake lock and the "Keep this page open" line make this rare.

## Open choices made

1. **Compression is marked by a prefix byte.** Protocol 2 plaintext starts with `0x02` (or `0x03` for a bundle); protocol 1 plaintext is bare JSON starting with `{`. The envelope layout itself doesn't change.
2. **Hellos stay in the protocol 1 layout,** so a host of any version can read one and answer with the version reply. This also covers a new participant meeting an old host's tab.
3. **Views carry `hostNow` on both paths,** and a view with the same `seq` is accepted when its `hostNow` is later, because presence, acks and rejects change without a new `seq`.
4. **Every flush publishes a bundle,** even if all participants are on the direct path, so the relay path is always current and the rule stays simple.
5. **Change bundles carry the entries changed since the last refresh**, whatever the person's path; full refreshes carry every attendee's entry.
6. **Items are signed with a raw signature and no public key,** because only the host's key can sign them, and the outer signature covers them through `itemsHash`.
7. **Rejects carry a message key, not the text,** to keep entries small.
8. **A view lists acks for at most three tabs per person,** the three with the most recent commands. This limits what is sent, not what is kept.
9. **A refused join gets a view with `joinRefused`,** because a hello has no ack to carry a reject.
10. **A stale tab is refused with `staleTab`** and asked to reload.
11. **The relay clock estimate** uses the largest `hostNow − receivedAt` over the last 8 bundles plus half the smallest of the last 8 echo latencies, and the direct estimate wins if a pong arrived in the last 30 s.
12. **Pings name their `peer`, their tab and a count,** like hellos and commands, so the host accepts each once, and pongs are matched to an outstanding `t0`.
13. **The size check measures personal entries at their largest,** so only topics and attendees can grow a board past the cap, and only through the commands that are checked.
